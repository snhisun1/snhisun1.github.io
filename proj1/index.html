Overview

In CS180, we've learned that with 3 grayscale red, green and blue exposures of the same scene, we can actually reconstruct the exact scene with full color. The problem is that combining the red, green and blue filters as color channels can reconstruct the color, but usually the exposures do not line up perfectly, so naively stacking them on top of each other produces odd, out of place artifacts.

Our goal is to estimate a horizontal and vertical translation for each channel, such that the filters line up to produce the accurate color version. My project starts with a exhaustive search on small images, extends that search with an image pyramid for larger ones, and then attempts to improve the matching features from brightness to gradient magnitude.

the scans

Each input is one grayscale scan with the blue, green, and red exposures stacked from top to bottom. The code uses one third of the scan’s height for each channel and also discards leftover bottom rows. I also convert 8-bit images to floating point by dividing by 255 and 16-bit images by 65,535, so both use the same numerical scale. After the algorithm aligns the channels, they are stacked in red–green–blue order and saved as JPG.

Every offset pair is (dx, dy), measured in pixels of the original channel image. Blue is held constant so its offset is always (0, 0). Example: green (2, 5) means moving green two pixels right and five pixels down.

Single-Scale Alignment

Searching for translations

For each of the two moving channels (blue is held constant) the first algorithm tries every integer offset from −15 to +15 in both directions, giving 31 × 31 = 961 candidates per channel. Each candidate offset receives a similarity score (calculated below), and the shift with the largest similarity score is selected. Throughout, green and red are each compared with blue, giving two offset vectors per image.

Normalized cross-correlation

The similarity score used is normalized cross-correlation (NCC), which is the dot product between two mean-subtracted, normalized vectors. Here, NCC compares the pixel intensity (brightness) patterns in each shifted green or red channel with those in the fixed blue channel. Basically, for two corresponding image sections A and B, subtract each sections’s mean brightness, multiply corresponding centered pixels, sum those products, and divide by the product of the centered sections’ lengths:

NCC(A, B) = Σ[(A − mean(A))(B − mean(B))]
÷ √{Σ(A − mean(A))² · Σ(B − mean(B))²}

Math jargon aside, this basically means that the NCC score is higher for patterns that brighten and darken together, so logically it should be measuring whether the structures line up across filters

Scoring windows of images

The scan borders are often noisy, so the reference window therefore excludes around 10% on each side (rounded down to whole pixels). The margin also will grow to accommodate the initial shift and the search radius. This keeps all slices inside the array and gives every candidate the same number of pixels.

Rather than create a shifted full image for every candidate, because it would be unnecessarily computationall expensive, the search just compares a fixed reference slice with a displaced slice of the moving channel. For a candidate (dx, dy), the moving slice starts at (top − dy, left − dx). This only changes how the candidate is evaluated (it is still exhaustive search). Once the best shift is found out of all the candidates, np.roll applies it to the full channel.

Multi-Scale Pyramid Alignment

An exhaustive search with larger windows is not feasible for the displacements in the larger (TIFF) scans because that would require many, many comparisons of large arrays and would be computationally expensive. So, we can take advantage of image pyramids: representing the images at multiple scales and processing from the coarsest scale and going down. The method roughly goes:

  1. Repeatedly halve each image dimension, using bilinear resizing with antialiasing, until the shorter side is at most 300 pixels.
  2. At the smallest level, search ±15 pixels around zero using intensity NCC.
  3. At each larger level, multiply dx by the width ratio and dy by the height ratio, then round to integer pixels.
  4. Search ±2 pixels around that scaled estimate, then continue to the next level.
  5. Shift the original-resolution green and red channels, combined with blue.

These settings are fixed for all images. I landed on these parameters after testing them, experimenting and balancing how effective each one was versus its speed. For example, increasing refinement radius past 2 leads to the same results but each pass through just takes a much longer time (because we are searching further)

Improvement: Gradient-Based Alignment

>The improvement keeps the same pyramid and displacement search and only changes what NCC compares. Instead of raw brightness, it compares edges, as the gradient magnitude is large wherever brightness changes quickly, which is oftentimes where object boundaries are.

Computing gradient magnitude

Horizontal and vertical derivatives are computed with central differences. For interior pixels:

Ix(y, x) = [I(y, x + 1) − I(y, x − 1)] / 2
Iy(y, x) = [I(y + 1, x) − I(y − 1, x)] / 2
M(y, x) = √(Ix² + Iy²)

The implementation computes these differences with NumPy slices at each pyramid level. It is quite intuitive: basically, for each pixel, look one step left and one step right and take the difference. The result is how fast brightness is changing horizontally. For the vertical change, do the same thing but up and down, then combine the two with the Pythagorean theorem to get a single number per pixel. The result is small in flat regions, and large wherever there is an edge. NCC then runs on these edges instead of on brightness.

There are two main features that make this an improvement. First, edges sit at object boundaries, and a boundary stays in the same place no matter how bright that material happens to be through a given filter. Further, squaring the derivatives throws away the direction the brightness was going, so an edge that runs dark-to-light in one plate still matches the same edge running light-to-dark in another (which is exactly what broke the previous algorithm on the Emir photo)

Emir: the main improvement

As discussed earlier, the brightness intensity NCC algorithm failed because the robe is bright in the blue plate and nearly black in the red one, and it occupies a large share of the image. Matching instead on gradients fixes the problem, as the edges of the robe's outline, the sash, and the face are in the same place in both plates regardless of how bright the fabric is in either one, so the correct shift scores best when matching edges
